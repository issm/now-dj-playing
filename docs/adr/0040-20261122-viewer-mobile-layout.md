# ADR-0040: viewer のモバイルレイアウト (viewer-web)

## ステータス

Accepted

## コンテキスト

ブラウザ版 viewer (viewer-web、ADR-0038) を、`https://ndp.iss.ms/v/` から配信している (ADR-0039)。モバイルで開くと、表示する情報の一部が画面に収まらず、スクロールが必要になった (#88)。

ADR-0007 のレイアウトは、iPad の横位置を前提にしていた。モバイルでは、次の問題があった。

- ルートが `h-screen` (`100vh`) のため、iOS のブラウザでは、ツールバーを含む高さになり、実際の表示領域より高い。下の情報がツールバーに隠れる
- ヘッダの高さ、アートワーク、文字サイズが固定値で、画面に応じて縮まない
- iPhone の横画面は、幅が `md` (768px) 未満になる場合があり、縦積みの配置になる。画面の高さが足りず、ロゴがアートワークに重なり、曲情報が画面外に出る
- 横画面のノッチ側のセーフエリアが、白く見える
- タブレットの縦画面では、横並びのレイアウトで上下に大きな余白ができ、アートワークが相対的に小さい

デスクトップ版 (Tauri、横長のウィンドウ) の見た目は、変えない。

## 決定

### ADR-0007 で決めていたことの、決めなおし

ADR-0007 で決めていた次の項目を、今回、下表のように決めなおした。表に挙げない項目は、この ADR では変えない。

| 項目 | ADR-0007 での決定 | 今回の決定 |
|---|---|---|
| ルートの高さ | `h-screen` (`100vh`) | `h-dvh` (`100dvh`) (1) |
| 横並びと縦積みの切り替え | 幅が `md` 以上なら横並び、未満なら縦積み | 横向きで幅 48rem 以上、またはスマホの横画面なら横並び。それ以外は縦積み (2) |
| 文字サイズ (曲名、アーティストなど) | `md` 以上はデスクトップ用、未満はモバイル用 | 横向きで幅 48rem 以上かつ高さ 30.0625rem 以上のときだけデスクトップ用。それ以外はモバイル用 (2) |
| アートワークの大きさ | モバイルは `w-64`。`md` 以上は親幅いっぱい (`max-h-full`、`max-w-[85vh]` で制約) | 横並びのときは、列の幅、列の高さ、画面高の 85% の最小値を一辺とする正方形。タブレットの縦画面は大きくする (3) |
| ヘッダの高さ | 15vh と記載。実装は `h-[100px]` の固定値だった | `6.25rem` (4) |
| モバイルの縮小 | 定めていない | `html` の `font-size` を 85% にする (4) |
| 入力欄の文字サイズ | 定めていない | コード入力欄は 16px 固定 (5) |
| セーフエリア | 定めていない | `html` と `body` の背景を黒にする (6) |

### 1. ルートの高さを `dvh` にする

`App.tsx` のルート要素を、`h-screen` から `h-dvh` にする。`dvh` は、ツールバーの出入りに追従する。デスクトップでは `vh` と同じ値になる。

`MonitorView.tsx` (モニタウィンドウ、Tauri のみ) の `h-screen` と、`BackgroundPicker.tsx` の `vh` は、変更しない。

### 2. レイアウトの切り替え条件を、向きと高さで決める

`index.css` に、Tailwind の `@custom-variant` を定義する。`App.tsx` の `md:` は、レイアウトに関するものを `wide:`、文字サイズに関するものを `desk:` に置き換える。

| バリアント | 条件 | 用途 |
|---|---|---|
| `wide` | 横向きで幅 48rem 以上、または、横向きで高さ 30rem 以下 | 横並び (アートワークが左、曲情報が右) にする |
| `desk` | 横向きで、幅 48rem 以上、かつ高さ 30.0625rem 以上 | デスクトップ用の文字サイズにする |
| `phone-landscape` | 横向きで高さ 30rem 以下 | スマホの横画面だけの調整 (左右の幅比率を 2 : 3 にする) |
| `tablet-portrait` | 縦向きで幅 48rem 以上 | タブレットの縦画面だけの調整 (アートワークを大きくする) |

端末ごとの結果は、次のとおり。

| 端末と向き | 配置 | 文字サイズ | 縮小 |
|---|---|---|---|
| iPhone 縦 | 縦積み | モバイル用 | 85% |
| iPhone 横 | 横並び (左 2 : 右 3) | モバイル用 | 85% |
| iPad 縦 | 縦積み (アートワークを大きくする) | モバイル用 | なし |
| iPad 横、デスクトップ | 横並び (左 1 : 右 1) | デスクトップ用 | なし |

### 3. アートワークの大きさ

- 横並びのとき、アートワークは「列の幅、列の高さ、画面高の 85% (`85dvh`)」の最小値を一辺とする正方形にする (container query の `cqw`、`cqh` を使う)。画像の枠と見える範囲が一致し、角丸が見える
- タブレットの縦画面は、幅を `min(70vw, 50dvh)` にする
- スマホの縦画面は、`w-64` (85% で約 218px) のままにする

### 4. モバイルの縮小は、rem の基準を下げて行う

- 幅が 48rem 未満、またはスマホの横画面のとき、`html { font-size: 85% }` にする。Tailwind の `w-*` と `text-*` は rem 基準なので、まとめて縮む
- px 固定だったヘッダの高さ (`h-[100px]`) と、ロゴの最大高さ (`max-h-[80px]`、`max-h-[60px]`) は、`rem` に直す (`6.25rem`、`5rem`、`3.75rem`)。1rem が 16px の画面では、値は変わらない
- メディアクエリの `rem` は、ブラウザの初期値 (16px) が基準で、`html` の `font-size` の影響を受けない

### 5. コード入力欄は、16px 固定にする

iOS は、フォーカスした入力欄の文字が 16px 未満だと、ページを自動でズームする。縮小で `text-base` が約 13.6px になるため、コード入力欄だけ `text-[16px]` (px 固定) にする。

### 6. セーフエリア

`html` と `body` の背景を黒にする。横画面のノッチ側のセーフエリアが、白く見えなくなる。`viewport-fit=cover` と `env(safe-area-inset-*)` は、使わない。

## 理由

- `dvh` は、ツールバーの出入りに追従する、標準の単位。JavaScript で高さを測るより単純
- 幅だけでなく、向きと高さで切り替えると、iPhone の横画面を、デスクトップ版のレイアウトに寄せられる。ADR-0007 の、アートワークを大きく見せる意図に合う
- 縮小に rem の基準を使うと、変更が少なく、レイアウトの寸法と一緒に縮む
- 入力欄のズームは、OS の挙動なので、文字サイズで避けるしかない

### 検討した代替案

- **`transform: scale`**: 見た目だけが縮み、レイアウト上の大きさが変わらない。周りに空きが残り、画面に収める目的に合わない
- **CSS `zoom`**: レイアウトも縮むが、ルート (`h-dvh`) にかけると高さも縮み、下に隙間ができる
- **`viewport-fit=cover` と `safe-area-inset`**: 背景色を黒にするだけで足りたので、使わなかった

## 影響

- デスクトップ版 (Tauri) の、幅 768px 以上の縦長のウィンドウ (高さが幅より大きい) は、縦積みになる。通常の横長のウィンドウは、これまでと同じ
- デスクトップ版の、高さ 480px 以下の横長のウィンドウは、85% の縮小と、モバイル用の文字サイズが適用される
- 横並びのとき、アートワークの角丸が、デスクトップ版でも見える (これまでは、枠が横長のとき、見えなかった)
- アーティスト名の行数に上限 (`line-clamp`) は、設けていない。約 80 文字 (3 行) までは、iPhone の縦横、iPad の縦横で、スクロールなしで収まることを、実機で確認した。さらに長い場合は、iPhone の横画面で溢れる可能性がある。問題が起きたときに、改めて issue にする
- コメントとタグは、viewer-web では表示しない前提のため、モバイルでの収まりは確認していない
- 検証は、実機 (iPhone と iPad の縦横) で行った。エミュレーションは、ツールバーの出入りを再現しないため、`dvh` の確認には使えない
- viewer-web の「切断時の再接続」(#99) など、モバイルの操作性に関する課題は、この ADR の範囲外
